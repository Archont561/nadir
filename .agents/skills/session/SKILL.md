# Session lifecycle for Nadir

A session is a five-phase loop: **(1)** enter the verified environment, **(2)** survey the
repository and backlog, **(3)** propose a bounded session and stop, **(4)** execute approved
work under the house rules, and **(5)** close the actual landed state with evidence and the
next session's opening prompt. Use the four literal output shapes in
[`standup-template.md`](standup-template.md): opening prompt, standup, task hand-off, session
report.

Two rules span the loop:

- **Proof boundary:** report only what this machine or CI actually proved. A missing network,
  native runner, real dataset, sandbox repack, or merged commit is an open item, not a checked
  criterion.
- **State preservation:** inspect branch and working tree before changing anything. Preserve user
  changes, stay on the assigned branch, and never reset, clean, stash, rebase, or switch branches
  just to make startup look tidy.

## 1. Enter the verified environment

### Inspect before restore

From the repository root:

```bash
git status --short --branch
git log -1 --oneline
command -v pixi >/dev/null 2>&1 && pixi --version || true
command -v pixi-sandbox >/dev/null 2>&1 && pixi-sandbox --version || true
```

A dirty tree may be the previous session's hand-off. Account for changed paths before editing;
never overwrite them without explicit user approval.

### Restore once, then use Pixi only

Nadir's `scripts/restore.sh` is generated by `pixi-sandbox init` and drives the verified binary
from the packed branch. The published bundle is `sandbox/developer-linux-64`; `pixi-sandbox.toml`
declares one `developer` bundle for the `default` environment with `cargo_vendor = true`.

The modern restore registers managed launchers by default (`PIXI_SANDBOX_USER_TOOLS=register`):
`pixi` and `pixi-sandbox` land in `~/.local/bin` and exec the manifest-verified tools under
`.pixi/tools/<platform>/`. A running shell does not reread profile edits, so put the user bin on
`PATH` after restore.

```bash
if ! command -v pixi >/dev/null 2>&1; then
  if test -x "$HOME/.local/bin/pixi"; then
    export PATH="$HOME/.local/bin:$PATH"
  else
    bash scripts/restore.sh
    export PATH="$HOME/.local/bin:$PATH"
  fi
fi

pixi --version
pixi-sandbox --version || pixi sandbox --version
pixi install --frozen --offline -e default
```

Do **not** source `.pixi/sandbox-env.sh`: current transports do not generate it, and this
repository intentionally uses Pixi as the only entrypoint. Do not run bare `cargo`, `rustc`,
`bun`, `turbo`, `python`, `maturin`, `ruff`, `lefthook`, `colmap`, or `gdal` for repository proof.
Use `pixi run ...` so the command sees the locked environment and the restored Cargo vendor.

If `scripts/restore.sh` cannot fetch `sandbox/developer-linux-64`, that is missing input on a
strict airlock. Do not install a different Pixi or pixi-sandbox by hand to compensate; ask for
the sandbox branch or a connected restore.

### Verify transport provenance

Read the restore manifest when present:

```bash
python - <<'PY'
import json, pathlib
p = pathlib.Path('.pixi/.restore-transport/.pixi-sandbox/manifest.json')
print(json.dumps(json.loads(p.read_text()), indent=2)[:4000] if p.exists() else 'no restore manifest')
PY
```

If the local restore transport is absent, inspect the packed branch instead:

```bash
git show origin/sandbox/developer-linux-64:.pixi-sandbox/manifest.json | sed -n '1,160p'
```

Record at least: `source.commit`, whether the lock digest matches this checkout's `pixi.lock`,
the Pixi and pixi-sandbox versions, `linkage`, platform, environment list, and Cargo vendor
metadata. A feature branch may be newer than the packed source commit while using the same locks;
that is usable, but say so. Changed `pixi.lock`, `Cargo.lock`, or `bun.lock` means the offline
transport is stale until repacked.

### Command entrypoints

Repository verbs are Pixi tasks. Use `--frozen` by default; add `--offline` when proving an
airlock-style run.

```bash
pixi run --frozen --offline gates          # lint + typecheck + test + version-check
pixi run --frozen --offline ci             # gates + build
pixi run --frozen --offline lint
pixi run --frozen --offline typecheck
pixi run --frozen --offline test
pixi run --frozen --offline build
pixi run --frozen --offline coverage
pixi run --frozen --offline xtask --help
pixi run --frozen --offline xtask test --package nadir-core
pixi run --frozen --offline xtask clippy --package nadir-engine
pixi run --frozen --offline bun x --bun backlog task list -s "To Do" --plain
pixi run --frozen --offline bun x --bun skills list
```

Facts that shape proof:

- `gates` deliberately excludes `advisories`, `publish-plan`, and `publish-dist`; they can need
  network/channel metadata and are explicit tasks.
- `ci` is local `gates + build`. GitHub CI additionally runs sandbox-plan validation, advisory
  scanning, and a release-binary smoke test.
- Rust repository automation lives in `crates/xtask`; Rust package scripts call it through Turbo.
  Add or extend an xtask subcommand rather than embedding complex shell in `package.json`, Pixi
  tasks, hooks, or workflows.
- The restored transport includes the Pixi environment and Cargo vendor. It does **not** promise
  `node_modules`; on a strict airlock without a materialized Bun workspace, Turbo/Biome/backlog
  commands may be unavailable. Report that as an environment limitation instead of pretending
  the full gate ran.

### Establish an honest baseline

Choose the strongest baseline this machine can run:

1. If the Bun workspace and Python editable install are available, run
   `pixi run --frozen --offline gates` and record the observed counts/verdict.
2. On a connected sandbox, run `pixi run --frozen setup` once, then `pixi run --frozen gates`.
3. On a strict airlock without `node_modules`, run the Rust-only proof through Pixi/xtask
   (`xtask fmt --check`, `xtask check --workspace --all-targets`, targeted `xtask test`, and
   doctests where possible) and record JS/Python/backlog proof as unavailable.

Never copy historical counts into the standup. The baseline is what was observed in this
session.

## 2. Survey repository state and backlog

1. **Sync knowledge, not branches.** If GitHub is reachable, run `git fetch origin` and compare
   the current branch with `origin/main`. Keep the assigned branch. If it is behind or diverged,
   report that before proposing edits; merge/rebase needs approval when it could disturb work.
2. **Load standing context.** Read `AGENTS.md`, `.knowledge/context.md`, `.knowledge/index.md`,
   and only the ADRs/references linked by candidate tasks. Manifests and current code outrank
   older design prose when they disagree.
3. **List open work.** Prefer
   `pixi run --frozen --offline bun x --bun backlog task list -s "To Do" --plain`. If the Bun
   workspace cannot be materialized, read `backlog/tasks/*.md` for discovery only and say that
   task metadata cannot be safely edited until the CLI is available.
4. **Resolve dependencies.** Read each candidate with
   `pixi run --frozen --offline bun x --bun backlog task <id> --plain`. A candidate is unblocked
   only when every dependency is `Done`. Order by priority high → medium → low, then ordinal;
   explain any spike that jumps the queue because it unlocks several tasks.
5. **Exclude landed work.** Check recent commits, merged PRs when GitHub is reachable, open PRs
   for the current branch, and current task status. Do not re-propose work just because a task
   record or sandbox branch lags; identify the stale record.
6. **Match scope to proof.** Separate locally provable slices from work requiring push, CI,
   sandbox repack, real imagery, native platform, or maintainer action.

## 3. Propose the session, then stop

Fill **Session standup** from template §2 and wait for the user to choose or amend the scope.
Do not claim a task, edit files, or begin implementation before approval. A standup must include:

- environment mode and transport provenance;
- exact baseline evidence and proof gaps;
- branch/worktree state;
- total open and unblocked work;
- 2–4 ordered candidates with dependencies and rationale;
- proposed slices, separating local proof from remote proof; and
- decisions that change implementation shape, each with a recommendation.

The stop is part of the protocol: backlog order is evidence, not permission to choose product
scope for the user.

## 4. Execute approved work

Follow `AGENTS.md` as the authority and the relevant task's acceptance criteria as the boundary.

1. Claim the task through Backlog.md:
   `pixi run --frozen bun x --bun backlog task edit <id> -s "In Progress" -a @me --plan "<approved approach>"`.
2. For code changes, use the TDD and refactor skills in order. Consult
   `.agents/skills/tdd/SKILL.md`, name the public seam, write the failing behavior test first,
   and implement the smallest green slice. Once green, consult `.agents/skills/refactor/SKILL.md`
   and clean up in small behavior-preserving steps with targeted tests after each meaningful
   change. Pure refactors need existing passing tests or characterization tests first.
3. Keep domain behavior in Rust. Python and TypeScript remain thin adapters over the versioned
   `nadir-protocol` → `nadir-engine` dispatcher.
4. Put complex Rust management in `xtask`, not shell. Package-level scripts should be small
   Turbo facades that call `cargo run --quiet --package xtask -- ...`.
5. Test the narrow package first, then the affected language/FFI boundary, then the strongest
   baseline available. New behavior needs regression evidence; a command that could not run is
   listed, not silently omitted.
6. Update task notes through the backlog CLI as evidence accumulates. Check an AC only after its
   proof (`--check-ac <n>`). Finish with a PR-ready `--final-summary`; use `task complete <id>`
   only when every criterion is proven.
7. Produce template §3 before committing. Make one focused Conventional Commit per task and run
   the commit-message check. Respect the hosting session's branch/push contract; push or open a
   PR only when the user has authorized that boundary.

Before hand-off, `git status --short` must contain only intentional paths, generated artifacts
must stay out of Git, and the evidence must name exact command results.

## 5. Close the session after work lands

A local commit, pushed branch, open PR, merged PR, and successful post-merge run are different
states. Report the one that exists.

1. If work merged or was pushed to `main`, inspect triggered workflows. Nadir expects `ci` and
   `publish sandbox`; a red run belongs to this session until diagnosed.
2. After `publish sandbox` succeeds, inspect
   `sandbox/developer-linux-64:.pixi-sandbox/manifest.json`. Its `source.commit` should name the
   new `main` tip, and its lock/vendor metadata should match the merged locks.
3. Complete task records only when all AC evidence exists. Leave the task `In Progress` when CI,
   repack, real dataset, platform, or user action remains pending; name that proof in notes and
   in the report.
4. Re-baseline the landed revision when this environment can do so without switching away from
   the assigned branch. Otherwise use successful CI as remote evidence and preserve local proof
   separately.
5. Fill template §4. End it with template §1, fully populated: this is the paste-ready opening
   prompt for the next session.

A session that lands nothing still closes honestly: `Landed: nothing`, exact branch and
working-tree state, decisions made, proof gathered, and the next concrete move. Do not
manufacture a commit merely to make the report look complete.
